# LTレビュー観点チェックリスト（汎用）

観点に書いてあるものはすべて確認する。書いていないものは「観点外の気づき」として末尾に別記する（AIは渡された観点しか見ないため、範囲を明示する）。

重要度：
- **高**：直さないと本番で困る（時間超過・事実の誤り・公開リスク・スライドが開けない）
- **中**：伝わり方が明確に悪くなる（主張のぶれ、原稿とスライドのずれ）
- **低**：好み・磨き込み

指摘の形式：`ID・重要度・対象・箇所・指摘・修正案`（例：R1・高・script.md・S2・…・…）

## 0. 元ネタの事前チェック（原稿を書く前に実施）
- [ ] 時間配分の合計が目標秒数以内か（「5分枠」なら話し終わりは4分30秒目標）
- [ ] 字数の記載が複数あって食い違っていないか
- [ ] 「事実（話した内容）」と「台本」で範囲や主張がずれていないか
- [ ] 台本にしかない記述（固有名詞・言い過ぎ・補足）の洗い出し

## A. 内容（事実との整合）
- [ ] 元ネタの事実にない主張・エピソードが足されていないか
- [ ] 範囲の限定（「〜のときだけ」）が元ネタと一致しているか
- [ ] 「これから」が未実行であることが明示されているか
- [ ] 専門用語に初出で説明が入っているか

## B. 主張・構成
- [ ] 伝えたいことが1つに絞れているか
- [ ] タイトルと締めの一文がずれていないか、締めでタイトルが回収されているか
- [ ] 山場が立っているか（前後に余計な文がない／削られていない）
- [ ] 山場のあとに新しい論点を足していないか
- [ ] 理由の言い方が逆の結論に聞こえないか
- [ ] 別々の事実を「ので」で因果関係にしていないか
- [ ] 具体例の数が絞れていて、見出しと話し出しの言葉が揃っているか

## C. 時間
- [ ] 字数を `scripts/pace.py` で実測したか（目安：1秒5字＝1分300字）
- [ ] **各スライド** 5.5字/秒以下か（平均ではなくスライドごと。一拍置くスライドはさらに余裕を）
- [ ] 削る候補が字/秒の高いスライドから選ばれ、削る順が書かれているか
- [ ] 削る順は「元ネタにない補足」→「主張を支える文」の順か

## D. 原稿 ⇔ スライド整合
- [ ] 枚数・順番・スライド番号が一致しているか
- [ ] スライドの文言が原稿の「スライドに載せる文言」と一字一句一致しているか
- [ ] 発表者ノートが最新の「話す原稿」と一致しているか（プログラムで突き合わせる）
- [ ] 原稿で話さない内容がスライドに載っていないか（逆も）

## E. スライド（HTML）
- [ ] 文字量：1枚3行・1行20字前後まで
- [ ] 可読性：見出し88px以上・本文48px以上（1920×1080基準）、コントラスト
- [ ] 図：矢印の向き・順序が読めるか、重なりがないか
- [ ] キー操作：←/→、Space、PageUp/PageDown（クリッカー）で動くか（コードを読んで確かめただけなら、そう書いて実機確認を本番前チェックに残す）
- [ ] オフライン：CDN・Webフォント・外部画像に依存していないか、`file://` で開けるか
- [ ] headless Chrome でスクリーンショットを撮って目視（はみ出し・白紙・段階表示で見出しが動かないか）
- [ ] プレースホルダ（「○○」など）が残っていないか、JSエラーがないか（発表者名が未定の「○○」は低・未決）

## F. 公開リスク
- [ ] 社内LTか社外LTかが確定しているか（未確定なら指摘）
- [ ] 実コード・ファイル名・リポジトリ名・サービス名が出ていないか
- [ ] 脆弱性の詳細（ライブラリ名・バージョン・CVE・未修正箇所）が出ていないか
- [ ] 技術スタックが推測できる固有名詞がないか（例：govulncheck → Go）
- [ ] 自社コードの弱点・会社・顧客が特定できる情報がないか

## G. 表記
- [ ] 表記揺れ、Markdownのエスケープ崩れ
- [ ] 耳で聞いて硬い言葉がないか（言い換えたら字数を数え直す）

## 範囲外
- 話し方・声量（原稿からは判断できない）
- 可読性に関わらないデザインの好み
- 元ネタの事実そのものの真偽（本人の経験として扱う）
