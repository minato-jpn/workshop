# LT Deck：原稿 → スライド → レビュー

入力は「話した内容のまとめ（事実）」と、あれば「台本の下書き」。成果物は次の3つ（すべて入力と同じディレクトリ `<LT>/` に置く）。

| 成果物 | パス |
| --- | --- |
| 発表原稿 | `<LT>/script.md` |
| HTMLスライド（オフライン可・発表者ノート付き） | `<LT>/slides/index.html` |
| レビュー結果 | `<LT>/review.md` |

元ネタのファイルは編集しない。git commit はユーザーに言われるまでしない。

## 0. 最初にユーザーへ確認すること（まとめて1回で聞く）

- 持ち時間（話し終わり目標は「持ち時間 − 30秒」が既定）
- 社内LTか社外LTか（社外なら実コード・脆弱性詳細・技術スタックが分かる固有名詞を出さない）
- 発表者名（未定なら「○○」のまま、本番前チェックに残す）

分からなければ既定値で進め、未決事項として最終報告に書く。

## 1. 体制を決める

`ListAgents` で同じディレクトリのピアセッションを確認する。ユーザーが言った数（「2つのペイン」など）より、`ListAgents` で数えた実際の数を優先する。指揮役（自分）は数に含めない。

通知の扱い：判断は、ピアからの完了報告メッセージで行う。idle 通知は「止まっている」ことの確認にだけ使い、それを受けて指示を出し直さない。

枚数の目安：1枚あたり約30〜35秒（3分なら5〜6枚、5分なら8〜9枚、10分なら15枚前後）。

- **3つ以上ある**：自分は指揮役。原稿／スライド／レビューを1つずつ割り当て、`SendMessage`（`notify_when_idle: true`）で指示する。
- **2つ**：原稿＋レビューを1つ、スライドを1つに割り当てる。
- **ない**：自分で 2→3→4 を順に行う。サブエージェントはユーザーが頼んだときだけ使う。

ピアへの指示に必ず入れること：役割、入力と出力の**絶対パス**、完了したら指揮役に `SendMessage` で報告すること、`notes/<役割>.md` に手順メモを残すこと、commit 禁止。ピアに送ったメッセージは、相手の権限モードによっては承認待ちになる。返事がなければユーザーに承認を促す。

### 並行の進め方（手戻りを減らす順序）

1. レビュー担当が元ネタを**事前チェック**する（`references/review-checklist.md` の0章）。その間に原稿担当は執筆、スライド担当はデザインと骨組み（フェーズ1）を進める。
2. 事前チェックの指摘を指揮役が判断し、原稿担当とスライド担当の両方に流す。
3. 原稿ができたら、スライド担当はフェーズ2に入る。同時にレビュー担当は原稿だけを先行レビューする（A・B・C・F・G）。
4. 原稿を修正したら、原稿担当は「スライドに載せる文言」の**差分だけ**を指揮役に報告する。指揮役はそれをスライド担当に転送する。
5. 両方が揃ったら最終レビューを行う（前回の指摘が直ったかの再確認と、D・E）。高・中の指摘を直して完了。

指揮役が判断に迷う点（字数と話す速さのどちらを優先するか、など）は、レビュー担当の修正案を既定として採用する。ユーザーの意図が関わる点（事実の範囲、社内か社外か）は、ユーザーに確認する。

## 2. 原稿（script.md）

手順：
1. **元ネタの時間と字数を検算する**（合計秒数が目標を超えていないか、字数の記載が食い違っていないか）。
2. 事実と台本を突き合わせ、台本にしかない記述に印をつける。補足は残すが削る候補にする。言い過ぎは外す。固有名詞の扱い：社外LTでは、技術スタック・サービス・会社が分かる語を一般的な言い方に置き換える。社内LTでは、聴衆が普段使っている語（GitHub、develop など）は残してよい。本人のたとえ（作品名など）は主張の一部なので残す。
3. 範囲の食い違い（「〜のときだけ」など）を1つに揃える。
4. 1スライドにつき要点は1つ。枚数は1章の目安（1枚30〜35秒）に従い、締めはタイトルの再掲にする。台本のスライド指示に「A → B」があれば段階表示とみなし、2枚に分ける（3章）。
5. 各スライドを次の固定形式で書く（`scripts/pace.py` がこの形式を読む）：

```markdown
## スライドN：パート名（M秒）

**スライドに載せる文言**

- 見出し：…
- 箇条書き：…

**話す原稿**

> …

**演出メモ**：…
**削る候補①**：…
```

   - 「スライドに載せる文言」は、台本の「スライド：」指示を元に、1枚3行・1行20字前後で決める。言葉は「話す原稿」の話し出しと揃える（言い換えると R 指摘になる）。
   - 削る候補がないスライドは `**削る候補**：なし` と書く。①②③は削る順の通し番号にする。

6. `python3 <このスキルのディレクトリ>/scripts/pace.py <LT>/script.md` で集計する。「このスキルのディレクトリ」は、この SKILL.md があるディレクトリ（読み込み時に表示される base directory）。html-ppt も同じ .claude/skills/ にある別のスキルなので、そちらのディレクトリと取り違えない。相対パスは実行場所でずれるので、両方とも絶対パスで渡す。冒頭に総字数、末尾に表を書く。上限を超えると exit 1。番号は通し番号（6a のような枝番も読めるが、通し番号を推奨）。

基準：
- 話す速さは **各スライド5.5字/秒以下**（平均ではなくスライドごと）。全体の目安は1秒5字。字数の目標より速さを優先する。
- 山場は削らない。山場のあとに新しい論点を足さない。
- 削る候補は字/秒の高いスライドから選ぶ。削る順は「元ネタにない補足」→「主張を支える文」。
- 理由の言い方が逆の結論に聞こえないか、別々の事実を「ので」でつないでいないかを確かめる。
- 言い換えたら必ず数え直す。字数はシェルの `wc -m` ではなく Python で数える（ロケール問題）。

## 3. スライド（slides/index.html）

`html-ppt` スキル（このスキルと同じ `.claude/skills/` にある）を読み込んでから作る。html-ppt から使うのは次のものだけ（LTではこのスキルの指示を優先する）。

- **assets**：base.css・runtime.js・テーマCSS1つを `slides/assets/` にコピー。fonts.css・animations.css は使わない（Webフォントとアニメを避ける）。
- **レイアウト**：`templates/single-page/` から1枚ごとに選ぶ。目安は、表紙＝cover、対比（想像と現実など）＝comparison、手順・回数＝process-steps、因果の流れ＝flow-diagram、箇条書き＝bullets、山場の一文＝big-quote、締め＝cta。選んだ結果を「No・パート・レイアウト」の表にしてから作る。
- レイアウトの CSS は各テンプレートの `<style>` に直書きなので、使うものだけ `slides/assets/layouts.css` にまとめ、**本文48〜52px・見出し88〜120px**に拡大する（テンプレートは12〜24px）。読み込み順は base.css → テーマ → layouts.css → style.css。`--text-3` は `--text-2` に置き換える。`data-anim`・絵文字アイコン・文言にない kicker／lede／tag／ボタン・見出しと役割が重なる飾り（番号の丸など）は外す。
- **構造**：`<section class="slide">`、`<aside class="notes">`、`?preview=N`。
- 使わないもの：full-deck テンプレート、new-deck.sh、render.sh（macOS用）、「最初にユーザーに3点聞く」、ノート150〜300字の目安。
- **配置**：見出しは上、その下の内容は残りの高さの中で縦中央に置く（例：`.stage{flex:1;display:flex;flex-direction:column;justify-content:center}`）。`.slide` 全体の中央寄せのままだと、内容が少ないときに上に寄って下が空く。1〜2字だけ次の行に落ちるときは `<br>` で意味の切れ目に改行する（check_slides.py はタグを無視する）。

- 自己完結フォルダにする：`slides/assets/` に base.css・runtime.js・テーマCSSをコピーし、CDNやGoogle Fonts（fonts.css）は読まない。日本語フォントは `--font-sans` に加えて `--font-display`・`--font-serif` も `"Noto Sans JP","Noto Sans CJK JP","Hiragino Sans","Yu Gothic",Meiryo,sans-serif` で上書きする（テーマ既定の Noto Sans SC／Noto Serif SC だと中国語の字形になる）。上書きする style.css はテーマより後に読み込む。テーマは文字中心なら japanese-minimal 1つでよい。
- 「スライドに載せる文言」は書き換えずに使う。「話す原稿」・秒数・演出メモ・削る候補は `<aside class="notes">` にだけ入れる（html-ppt の説明は `div.notes` だが、check_notes.py は aside を読む）。S キーで発表者ウィンドウ、N キーでノート。
- ノート内の書式（check_notes.py の照合規則）：秒数・演出メモは `<p class="cue">…</p>` に書く（照合から外れる）。削る候補は `［削る候補①：最初に削る］<span class="cut">本文</span>` と書く（［］の中だけ外れ、本文は照合される）。
- 文字サイズは1920×1080基準で、見出し88〜120px・本文48〜52px。強調する一文は1枚につき1つ。
- 図（循環図など）はインラインSVGで描き、色はテーマの変数を使う。ページ番号は自分で振る（runtime.js は最初の `.slide-number` しか更新しないので、全スライドの `.slide-number` に通し番号を入れる数行のスクリプトを足す）。
- 段階表示（話の途中で文字を出す）は runtime が対応していない。必要なら**スライドを2枚に分け**、前のスライドには後で入る部分と**同じ大きさの空の枠**（点線）を置いて、共通部分の位置を固定する。文字を `visibility:hidden` で隠して置く方法は、話していない文言が残るので使わない。後のスライドで増える部分以外のアニメは外す。確認は、shoot.sh の2枚の画像の差分が「増えた部分とページ番号だけ」であること。さらに、base.css は切り替え時に前後のスライドを±30pxずらしてフェードするので、静止画で動かなくてもキー送りでは揺れる。分けたスライドの**組全体**（例：S2〜S5）に `hold` クラスを付け、`.slide.hold,.slide.hold.is-prev,.slide.hold.is-active{transform:none;transition:none;background:var(--bg)}` を style.css に足す（片側だけに付けると、逆向きに戻るときに画面が一瞬空になる。背景を不透明にするのは、フェード中の前後のスライドが透けないようにするため）。この組への出入りは一瞬で切り替わる。切り替え途中は shoot.sh で撮れないので、ブラウザで → と ← を押して目で確かめる。原稿も切り替え位置で分け、秒数を割り振る。
- 文字色のコントラストは背景に対して3:1以上にする（html-ppt の `--text-3` は約2.8:1で足りない。補足は `--text-2` を使う）。
- 本番前チェックに次を書く：T キー（テーマ）と A キー（アニメ）は1キーで切り替わるので押さないこと。フォントと S キーの発表者ウィンドウの同期は、本番のPCで確認すること。
- 確認（スクリプトはこのスキルの `scripts/` にある。パスは絶対パスで渡す）：
  - `python3 <スキル>/scripts/check_notes.py <LT>/script.md <LT>/slides/index.html`：ノートと「話す原稿」を全スライドで照合する。不一致があれば exit 1 で、差分を表示する。
  - `bash <スキル>/scripts/shoot.sh <LT>/slides/index.html <出力先> [枚数]`：headless Chrome で全スライドを撮影する（?preview=N で開き、トランジションは無効）。白紙があれば exit 1。撮った画像（grid.png があればそれ）は必ず目で見る。出力先はスクラッチなど、`<LT>/` の外にする。
  - `python3 <スキル>/scripts/check_slides.py <LT>/script.md <LT>/slides/index.html`：「スライドに載せる文言」が各スライドに表示されているかを照合する（「ラベル：値」の値で照合。ラベルが「図」で終わる行と「（照合しない）」の行は対象外）。見つからない文言があれば exit 1。
  - キー操作（←/→・Space・PageUp/PageDown）を runtime.js のコードで確かめただけなら、そう書き、実機での確認を本番前チェックに残す。
  - html-ppt の render.sh は macOS 用なので、Linux では使わない。

## 4. レビュー（review.md）

`references/review-checklist.md` の観点で確認する。ファイルは直接編集しない。指摘は `ID・重要度・対象・箇所・指摘・修正案` の形式で review.md に書き、観点外の気づきは末尾に別記する。2回目以降は、前回の指摘IDが直ったかを先に確認する。

- 1セッションで行うとき：review.md を書き終えてから、原稿・スライド担当に戻って高・中を直す。そのあと review.md に「2回目の確認」を追記し、pace.py・check_notes.py・check_slides.py・shoot.sh をやり直す。
- 本人の言葉の言い換え（意図に関わる点）は直さず、「本人判断」として修正案を添えて残す。
- 「○○」（発表者名が未定）は既定の状態なので「低・未決」にし、本番前チェックに残す。

## 5. 完了報告

ユーザーに次を伝える：成果物のパス、枚数・総字数・合計秒数・最大字/秒、見方（S/N キー）、残った未決事項（名前、社内か社外か、段階表示など）、本番前チェック（通し練習で持ち時間 − 30秒以内に収めること）。
