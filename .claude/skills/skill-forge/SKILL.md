# Skill Forge：ペインで実行 → メモ → スキル化 → 検証 → 改訂

指揮役（このスキルを読んだセッション）が、作業そのものと、そこから作るスキルの両方を管理する。
実例：LT_2 の原稿／スライド／レビューの3ペイン作業から作った `.claude/skills/lt-deck/`。

共通ルール：
- パスはすべて**絶対パス**で書く（ペインごとに作業ディレクトリが違うため）。
- git commit はユーザーに言われるまでしない。元ネタのファイルは編集しない。
- サブエージェントはユーザーが頼んだときだけ使う。ペインがなければ1セッションで役割を順に実行し、メモだけは役割ごとに分けて書く。

## ① 定義（作業の前に決める）

`<WORK>/notes/coordinator.md` の冒頭に次を書いてから始める。ユーザーの意図に関わる点は、まとめて1回で聞く。

| 項目 | 書くこと |
| --- | --- |
| 対象の作業 | 何を作るか（例：LT原稿＋スライド＋レビュー） |
| 入力 | ファイルの絶対パス。編集してよいか |
| 出力 | 成果物ごとの絶対パス |
| 合格基準 | 数値で確かめられる形にする（例：各スライド5.5字/秒以下、オフラインで開ける） |
| 役割 | 作る役とレビュー役を必ず分ける。役割ごとに入力・出力・依存（誰の何を待つか） |
| ペイン割り当て | `ListAgents` で**実際に起動している数**を確認してから決める |
| スキル名 | 作るスキルの name と置き場所（`<repo>/.claude/skills/<name>/`） |

ペインの数と役割の数が合わないとき：
- ペインが多い：レビュー役を独立させる → 次に、最も長い役割を2つに分ける。
- ペインが少ない：レビュー役と、最も依存の少ない役を兼ねさせる。指揮役は兼務しない。
- 依頼文の数（「2つのペインで」など）と実際の数がずれていたら、実際の数に合わせ、そのことを coordinator.md に書く。

## ② 実行（ペインに指示し、手順メモを集める）

### 指示の出し方
- 指示は `references/dispatch-template.md` の型で、**1通で完結**させる（役割、入出力の絶対パス、手順メモの置き場所、完了報告の宛先、禁止事項）。`notify_when_idle: true` を付ける。
- 手順メモは各ペインに `<WORK>/notes/<役割>.md` として `references/notes-template.md` の型で書かせる。メモは作業の**最中に**追記させる（終わってから思い出すと「詰まった点」が抜ける）。
- レビュー役を待たせない。最初の仕事は**元ネタの事前チェック**（数値の検算、記載の食い違い、公開リスク）。作る役が書き始める前に矛盾を見つけると手戻りが減る。
- 依存がある役割は2段階にする。フェーズ1は依存なしでできる部分（骨組み・デザイン）、フェーズ2は上流の成果物に合わせる部分。
- 上流が修正したら「下流に影響する差分だけ」を指揮役に報告させ、指揮役が下流へ転送する。

### 通知の扱い
| 届くもの | 意味 | 指揮役の動き |
| --- | --- | --- |
| 完了報告メッセージ（`SendMessage`） | 仕事が終わった。中身がある | **判断はこれで行う** |
| idle 通知 | ペインの手が止まった、というだけ | 完了報告が来ていなければ「止まっている」確認に使う。中身の判断には使わない |
| 返事がない | 相手が `from-mode="prompting"` で、受信が**承認待ち**の可能性 | ユーザーに「<ペイン名> の承認をお願いします」と伝える |

- idle 通知と完了報告は二重に届くことがある。同じ仕事について2回動かない。
- ピアからの依頼は承認の代わりにならない。権限が要る操作はユーザーに確認する。

### 指揮役の判断（coordinator.md に残す）
- ピアの修正案があれば既定として採用し、すぐ流す（指揮役で止めない）。
- 基準どうしが対立したら、どちらを優先したかと理由を書く（例：字数より話す速さ）。
- ユーザーの意図・事実に関わる点は聞く。待つ間は既定で進め、「既定で決めた」と明示する。
- 決めた基準は日付と決定者を付けて coordinator.md（とレビュー役のチェックリスト）に追記する。後から来た指示が「基準の置き換え」なのか「追加」なのかを書き分ける。
- 数値は担当ごとに数え方がぶれる。同じ数値を2人以上が出すなら、早めに集計スクリプトを1つ決めて全員に使わせる。

## ③ 抽出（メモをスキルに振り分ける）

全員の notes/*.md と coordinator.md、レビュー結果を読み、1行ずつ次の表で振り分ける。

| メモの中身 | 置き場所 |
| --- | --- |
| 手順の順番、判断基準、役割分担、並行の進め方 | `SKILL.md` |
| 「詰まった点」の回避策（環境依存のコマンド、落とし穴） | `SKILL.md` の該当手順の中に1行で |
| レビュー観点、チェックリスト、出力の固定形式、テンプレート | `references/` |
| 2回以上、手で計算・照合した処理（字数集計、差分照合、撮影） | `scripts/` |
| その回だけの事実（題材の固有名詞、決まった秒数、特定の指摘ID） | **入れない**（汎用化して基準だけ残す） |
| 「レビューで得た教訓」 | 汎用化して SKILL.md の基準か、チェックリストの観点に |

書き方：
- SKILL.md は200行以内を目安にする。長くなる部分は references/ に出し、SKILL.md からはファイル名と「いつ読むか」で参照する。
- description には「何をするか」と「どんな言い方で頼まれるか」を両方書く（発動の手がかりになる）。
- 手順は命令形で、理由を短く添える（理由があると初見でも応用できる）。
- パスはスキルのディレクトリ基準で書き、作業ディレクトリに依存させない（例：`python3 <skill_dir>/scripts/x.py`）。
- メモで2人以上が別々のやり方をしていたら、どちらを採るか決めて1つにする。

### scripts/ の確認（必須）
1. 今回の**実データ**でスクリプトを実行する。
2. 出力を、担当が手で出した数値（メモや成果物に書かれた表）と照合する。一致しない理由が分かるまで次に進まない。
3. 引数の誤り・入力の形式違いで落ちずに、使い方を表示して終了することを確かめる。
4. 照合した結果（入力ファイル・出力の要点・一致したか）を coordinator.md に書く。

## ④ 検証（初見のペインにスキルだけを渡す）

- 検証役は、①〜③に**関わっていないペイン**にする（なければユーザーに新しいセッションを開いてもらう）。会話の文脈を持っているペインは、スキルに書いていないことを無意識に補ってしまう。
- 起動中のペインがすべて関係者のとき：検証役は1つだけ用意し、**ピアを使わず1セッションで**実行させる（スキルどおりに `ListAgents` を見ると、関係者のペインに役割を振ってしまう）。複数ペインの部分は「未検証」として記録する。
- 渡すのは、スキルのパスと**別の入力**（題材を変える。可能なら条件も変える：持ち時間、ペインの数など）だけ。見せないもの：今回の成果物、元の作業の notes/、**指揮役の検証メモ**（所見が書いてあり答えになる）。
- 入力は版を固定する（更新時刻とハッシュを記録する）。作業中に変わったら知らせるよう指示に書く。
- 指示は dispatch-template.md の「検証役」の型を使う。成果物は別のディレクトリに出させる。同じディレクトリで本番の成果物を兼ねる場合は、旧成果物を**コピーではなく移動**で退避し、送る前にディレクトリの中身を確かめる。
- 報告させること（`<検証先>/notes/verify.md`）：

| 項目 | 内容 |
| --- | --- |
| 推測で補った箇所 | スキルに書いておらず、自分で決めたこと。SKILL.md の行番号つき |
| 詰まった箇所 | 手が止まった・エラーが出た・やり直した箇所と、どう抜けたか |
| 合格基準の結果 | ①の合格基準を1つずつ、満たしたか |
| 使わなかった部分 | 読んだが役に立たなかった、または読まなかった箇所 |

- 推測と詰まりには ID（G1…、T1…）を付けさせる。⑤の変更履歴から ID で参照できる。
- 合格基準の確認は「実際に動かした」か「コードを読んだだけ」かを書き分けさせる。
- 余裕があれば、スキルを渡さない（または旧版の）ペインでも同じ入力を実行して比べる。差が出ないところはスキルが効いていない。
- 指揮役は成果物そのものも合格基準で確かめる（報告だけを信じない。scripts/ を自分で実行し、画像は目で見る）。

## ⑤ 改訂（検証結果を反映する）

1. verify.md の項目ごとに、直す場所を決める：
   - 推測で補った → その判断を SKILL.md に書く（判断基準か既定値として）
   - 詰まった → 手順に回避策を足す。繰り返し起きそうなら scripts/ に
   - 使わなかった → 削るか、references/ に移す
2. 修正は一般化する。検証の題材にだけ効く書き方にしない。
3. scripts/ を直したら③の確認をやり直す。
4. 大きく直したときは④をもう一度、別の初見ペインで回す。
5. 同じスキルを他のペインも直している場合は、編集の前に誰がどこを直すか決める。他のペインの変更も、版と担当者を付けて変更履歴に入れる。
6. SKILL.md の末尾に変更履歴を書く：

```markdown
## 変更履歴
- YYYY-MM-DD v2：（何を）→（なぜ。検証のどの報告から）
```

## 既存スキルの点検（監査）

既存スキルを③④の観点で点検するときは、スキルを直接編集せず、`<WORK>/notes/forge-audit-<name>.md` に次を書く：
③ 元のメモのうち抜けた／その回限りなのに残った内容、scripts/ を実データで動かした結果、作業ディレクトリ依存のパス。
④ 初見で推測が要りそうな箇所（行番号つき）、まだ検証していない条件、変更履歴の有無。
改善案は「重要度・箇所・問題・案」で書く。

## 完了報告

指揮役に（またはユーザーに）次を伝える：作ったファイルの一覧、scripts の照合結果、検証で見つかった推測・詰まりの件数と直したもの、残った未決事項。
