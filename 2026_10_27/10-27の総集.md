# データフェッチ on Server Components

データフェッチにおいて、通信回数と責務がトレードオフになりがちです。通信回数を減らすということは色んな情報を一度のAPIで取得することになり、責務が増えることになります。

問題として、<=なぜ??

- 変更が容易でなくなる
- API自体のパフォーマンス問題が起きる。

一方、責務を意識して、小さな単位でデータフェッチをすると通信回数が増えてしまいます。
これは問題として、通信回数が増えると、ユーザー体験の低下や、サーバーへの負荷が増えること、フェッチされたデータに基づいて子コンポーネントがフェッチを行うウォーターフォールが発生しやすくなります。

## クライアントサイドのデータフェッチの問題点

基本的にクライアントサイドでのデータフェッチを行った場合には、Next.jsのサーバー側でのフェッチにならないため、APIキーやトークンをサーバー側で持たないことになります。ブラウザから直接APIが届く必要があるので、APIを公開しないといけないのでセキュリティの問題にさらされます。
クライアントサイドでのフェッチはJSや表示されない可能性のある不要なコンポーネントをブラウザ側に送信するので、バンドルサイズが大きくなりガチである。

こういった問題はサーバーコンポーネントからの呼び出しにしてしまえばNextJSのサーバー側でフェッチが行われるので、APIキーやトークンをサーバー側で持つことができ、セキュリティの問題を回避できます。また、不要なコンポーネントをブラウザに送信する必要がなくなるので、バンドルサイズも小さくなります。

fetch(ブラウザ) -> BFF API(public) -> backend API(private)
これだと結局BFF APIを公開する必要があるので、セキュリティの問題は回避できません。


## BFFとサーバーコンポーネントとコロケーション

サーバーコンポーネントで実装するということはコンポーネントそれぞれがでBFFを作り、それぞれがAPIを投げるということになります。
ということはデータフェッチはコンポーネントの責務として働くことになり、サーバーコンポーネントでデータフェッチの処理が記述されます。この状態をコロケーションと呼びます。

なんだかんだ言って責務を意識して小さな単位でデータフェッチを行うことは、通信回数が増えるという問題はありますが、変更が容易であり、API自体のパフォーマンス問題も起きにくいです。

またリクエストの内容がサーバーのキャッシュに保存され、同じリクエストが来た場合にはキャッシュから返すことができるので、通信回数が増えるという問題も解決できます。

## リクエストのメモ化

同じリクエストである条件として同一URLであり、同一オプションであることが必要です。オプションの指定ミスによりメモ化できなくなるので、データフェッチ処理はそれぞれのコンポーネントに直書きするのではなく、fetcherとして共通化しておくと良いです。

## 並行データフェッチ

冒頭でお話した内容ですが、データフェッチの単位を小さくするとデータフェッチに依存したデータフェッチが発生しやすく、またそれによってウォーターフォールが発生してしまいます。これについての解決策についてお話しました。

### データフェッチ単位でコンポーネントの分割を行う

ページレベルで並行でデータのフェッチを行うことができる構造にする。

```typescript
// これだとcommentsまではレンダリングされるが、commentのレンダリングはcommentsのデータフェッチが完了するまで待たされる。
<page>
<comments/>
</page>
```

```typescript
// comments.tsx
// 平行にレンダリングされる
return (
<page>
 <comments>
   <comment/>
   <comment/>
   <comment/>
 </comments>
</page>

```

### プリロードパターン

ページレベルでデータフェッチを行うことで画面のレンダリングのタイミングでデータフェッチをなげて、コンポーネントのレンダリングの前にメモ化される。孫コンポーネントがデータフェッチを行う場合でも、同じリクエストであればキャッシュから返すことができるので、ウォーターフォールが発生しにくくなただこれだと、親コンポーネントレベルでのフェッチ処理になっており、コロケーションの責務を意識したデータフェッチの設計から外れてしまいます。

DataLoaderを利用することでそれを守ることができます。取得処理は一度であるが、コンポーネントごとのデータフェッチをコード上では実行されている形にすることができました。

ただ、コロケーションを採用した状態での並行のデータフェッチを行う場合にはN + 1問題が発生する可能性があります。一つのリクエスト（コンポーネント）を呼び出すと結局それに依存する（子または孫）のリクエストが発生してしまうので依存するコンポーネントレンダリングの数だけフェッチされてしまいます。

対策として、APIのクエリパラメータやリクエストボディに複数のIDを渡すことでまとめてデータの取得をするリクエストを一度だけ投げることで解決されます。

ただこれだと、親コンポーネントレベルでのフェッチ処理になっており、コロケーションの責務を意識したデータフェッチの設計から外れてしまいます。

DataLoaderを利用することでそれを守ることができます。取得処理は一度であるが、コンポーネントごとのデータフェッチをコード上では実行されている形にすることができました。
