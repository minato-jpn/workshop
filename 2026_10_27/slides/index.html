01 · trade-off

通信回数を減らすか、責務を小さくするか

まとめて 1 回で取る

  • 通信回数は少ない
  • 1 つの API が色々な情報を返す → 責務が増える
  • 変更が容易でなくなる
  • API 自体のパフォーマンス問題が起きる
⇄

小さな単位で取る

  • 責務が明確で変更しやすい
  • ただし通信回数が増える
  • UX の低下・サーバー負荷の増加
  • 親のデータを待って子が取る ウォーターフォールが起きやすい

今日のゴール：小さな単位で取る設計を選び、そのデメリットを Next.js / React の仕組みで潰す

02 · client-side fetch

ブラウザから fetch すると何が困るか

🔓 セキュリティ

ブラウザから直接 API に届く必要があるので、API を公開しなければならない。API キーやトークンをサーバー側に閉じ込められない。

📦 バンドルサイズ

フェッチ処理の JS や、表示されないかもしれないコンポーネントまでブラウザに送ることになり、バンドルが大きくなりがち。

🐢 往復が直列に重なる

HTML → JS 読み込み → ハイドレーション → fetch(id 一覧) → fetch(中身)。ブラウザ⇔サーバーの往復が積み重なる。

Server Component から呼べば、フェッチは Next.js のサーバー側で実行される → キーを隠せて、余計な JS も送らない

03 · colocation

データフェッチをコンポーネントの責務にする

Server Component では、各コンポーネントが自分に必要なデータを自分で取る。データの取得とその使い道が同じ場所に書かれる状態をコロケーションと呼ぶ。

小さな単位なので変更が容易で、API のパフォーマンス問題も起きにくい
増える通信回数は、サーバー側のキャッシュ(メモ化)で吸収する → 次のスライド

04 · request memoization

同じリクエストは 1 回にまとまる

1 回のレンダリング中に同じリクエストが複数回呼ばれても、結果がメモ化されて実際の取得は 1 回になる。

「同じリクエスト」の条件

同一 URL かつ 同一オプション。オプションの指定ミスでメモ化が効かなくなる。

だからフェッチ処理はコンポーネントに直書きせず、fetcher として共通化しておく

04 · anti-pattern

メモ化がないと 3 か所で 3 回取る

❌ /anti/no-memoization/[id]

  • generateMetadata
  • ページ本体
  • 子コンポーネント Detail
  • → getProductNoCache がログに 3 回
→

✅ /products/[id]

  • 同じく 3 か所で getProduct を呼ぶ
  • メモ化により DB アクセスは 1 回
  • ページで取って props で渡す必要がない
  • → バケツリレーを避けつつ重複もしない

重複を避けるためにページで取得して props で渡すと、今度はバケツリレーになる。メモ化があるから各コンポーネントで気軽に呼べる。

05 · parallel fetch

小さく取ると、ウォーターフォールが起きる

データフェッチに依存したデータフェッチが直列に並び、待ち時間が積み重なる。

❌ 直列(preload なし)

getProduct
500ms
getProductIds
500ms

合計 ≒ 1000ms

✅ 並行(preload あり)

getProduct
500ms
getProductIds
500ms

合計 ≒ 500ms

対策：データフェッチの単位でコンポーネントを分割し、ページレベルで並行に取れる構造にする

05 · preload pattern

await の前に、取得だけ始めておく

ページのレンダリング時にリクエストが投げられ、子・孫コンポーネントはメモ化された結果を受け取る

06 · N+1

コロケーション × 並行フェッチ = N+1 問題

一覧を取るコンポーネントの下で、各カードが 1 件ずつ取るとカードの数だけフェッチが飛ぶ。

06 · batching

まとめて取れば解決…でもコロケーションが崩れる

バッチ API を親で呼ぶ

  • クエリパラメータ / ボディに複数 ID を渡す
  • リクエストは 1 回で済む
  • でも親コンポーネントレベルのフェッチになる
  • 子は props で受け取るだけ → コロケーションから外れる
→

DataLoader を挟む

  • コード上は各コンポーネントが自分で 1 件ずつ取る
  • 同じタイミングの呼び出しを DataLoader が集める
  • 実際の取得はバッチ API の 1 回だけ
  • → コロケーションと通信回数を両立

06 · dataloader

DataLoader をリクエストごとに 1 つ作る

Card ごとに getProduct(id) を呼んでも、ログは getProductsByIds [1, 2, 3] の 1 回

⚠️ モジュールスコープで new しない

DataLoader 自身もキャッシュを持つため、モジュールスコープで作るとプロセス全体で共有される。別ユーザーのリクエストに古いデータや他人のデータが漏れる。

デモ：/anti/shared-loader/[id] で DB の価格を変えてリロード → 古い価格のまま

// takeaways

まとめ

1 · サーバーで取る

Server Component でフェッチすれば API を公開せず、余計な JS も送らない。

2 · コロケーション

データは使うコンポーネントが自分で取る。小さな単位で変更に強い。

3 · fetcher を共通化してメモ化

同一 URL・同一オプション / React.cache で重複を 1 回に。バケツリレー不要。

4 · preload で並行化

await の前に取得を始めて、ウォーターフォールを避ける。

5 · DataLoader で N+1 を解消

コード上は 1 件ずつ、実際は 1 回のバッチ取得。

6 · DataLoader はリクエスト単位

cache(() => new DataLoader(...))。モジュールスコープは情報漏洩の原因。
